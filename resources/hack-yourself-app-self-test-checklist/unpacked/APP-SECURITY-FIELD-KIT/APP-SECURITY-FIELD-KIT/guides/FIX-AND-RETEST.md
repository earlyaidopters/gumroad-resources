# A result becomes useful when you can verify the repair

## First, verify the finding

Confirm the active session, account role, record owner, and intended sharing rule. Match the claimed impact to the returned evidence. A publicly intended document or a successful HTTP response with an empty body may not show a leak. A leaked privileged key is different from a public browser client key.

## Change the rule at the right layer

If the underlying request is wrong, repair the server, database policy, or trusted business logic that authorizes it. A disabled button, obscured organization ID, or unlinked page is not the same as an access check. Review related tables and routes rather than applying a one-URL patch.

## Keep a before and after

Record the original input and observed result with secrets removed. Apply the reviewed change in staging and record its version. Repeat the identical forbidden action, then the normal owner's action. Check adjacent operations affected by the repair. Use templates/RETEST.csv to keep the evidence together.

## Prepare the production change

Use your normal review and deployment process. Keep a rollback plan. A test against a local copy does not prove that production runs the same fix. After an authorized deployment, repeat a bounded check against that exact version and environment.

## If a real exposure is found

Stop the test and use the owner's incident process. Consider containment, access revocation, evidence preservation, and the appropriate qualified assistance. Do not delete evidence, publish an exploit, or assume a particular notification obligation from this kit.

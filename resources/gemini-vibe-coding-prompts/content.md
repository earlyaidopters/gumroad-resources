## **AI Text Humanization Tool**

```
Okay, world-class prompt engineer, designer, and product leader! Based on the walkthrough of the Grammarly interface and your specific goal of creating a similar but distinct tool focused on humanizing AI-generated text, here is a prompt designed for Lovable.dev:

## Lovable.dev Prompt: Design for "AuthenticText" - AI Humanization Tool

**1. Persona & Role:**
Act as an expert UI/UX designer and product leader tasked with creating the interface for a new web application called "AuthenticText". You understand the nuances of designing tools for writers and content creators, particularly the need to refine AI-generated content. Your design should prioritize clarity, ease of use, and actionable insights.

**2. Application Concept: AuthenticText**
AuthenticText is a web application designed to help users refine AI-generated text, making it sound more human, natural, and engaging. Users upload or paste text documents (articles, emails, reports, etc.) generated by AI tools. The application analyzes the text not just for grammatical errors, but specifically for patterns, phrasing, tone, and flow that indicate robotic or unnatural writing. It then provides targeted suggestions to improve authenticity and human connection.

**3. Inspiration & Constraints:**
*   **Structural Inspiration:** Draw inspiration from the structure and user flow observed in the Grammarly application (video provided implicitly), particularly its:
    *   Left sidebar navigation for core sections.
    *   Dashboard view for managing documents.
    *   Dedicated view for document analysis with suggestions.
    *   Settings area for customization (Account, Preferences, Dictionary).
    *   Features like Version History and Trash.
*   **Functional Focus:** The *core differentiator* is the analysis focus. Suggestions should target:
    *   **Robotic Phrasing:** Identifying and suggesting alternatives for overly formal, repetitive, or cliché AI phrases.
    *   **Tone Adjustment:** Helping users shift the tone to be more conversational, empathetic, confident, etc., as desired.
    *   **Flow & Readability:** Improving sentence structure variation and transitions.
    *   **Human Idioms/Expressions:** Suggesting appropriate colloquialisms or natural language use (where applicable and configurable).
    *   **Over-reliance on Specific Structures:** Flagging repetitive sentence beginnings or formats.
*   **Visual Style:**
    *   **DO NOT** replicate Grammarly's green color scheme or exact visual elements.
    *   **DO** aim for a clean, modern, trustworthy, and professional aesthetic.
    *   **DO** consider using subtle, elegant gradients (e.g., two-tone blues, purples, or teals) for primary action buttons, highlights, or section headers, similar to the *concept* of gradients in modern SaaS apps, but create a unique identity for AuthenticText.
    *   Ensure clear visual hierarchy and intuitive button placement.
    *   Typography should be highly readable.

**4. Key Sections & Features to Design:**

*   **A. Overall Layout:**
    *   Persistent left sidebar navigation.
    *   Main content area that changes based on the selected section.

*   **B. Dashboard / Documents View:**
    *   **Purpose:** The user's entry point and document management hub.
    *   **Elements:**
        *   Clear "New Document" (paste/type) and "Upload File" buttons (prominently placed, perhaps top-center or top-right).
        *   Search bar for documents.
        *   List/Card view of recent documents, showing: Title, snippet/preview, date last modified, maybe a quick "Authenticity Score" indicator.
        *   (Optional) A "Get Started Checklist" or quick tour prompt for new users.

*   **C. Document Analysis & Editor View:**
    *   **Purpose:** The core workspace where users interact with their text and the AI suggestions.
    *   **Layout:** Consider a two-or-three-column layout:
        *   Main area: The document text itself. Highlighted sections indicate areas with suggestions.
        *   Right sidebar: Detailed suggestion cards corresponding to the highlights.
    *   **Suggestion Cards:** Each card should clearly state:
        *   The issue (e.g., "Robotic Phrasing," "Unnatural Tone," "Repetitive Structure").
        *   A brief explanation of *why* it's flagged.
        *   One or more specific suggestions for change (e.g., rephrased sentences, alternative words).
        *   Buttons: "Apply Suggestion," "Ignore," maybe "See More Options" or "Rephrase Differently".
    *   **Editor Toolbar:** Basic text formatting options, plus controls like "Re-analyze Document," "View Version History," "Save."

*   **D. Settings Section (break down into sub-sections in the sidebar):**
    *   **i. Profile/Account:** User details (Name, Email), Password management, Linked accounts (e.g., Google Sign-in option). Option to Delete Account.
    *   **ii. Analysis Preferences / Customization:**
        *   Controls to tailor the analysis engine:
            *   Desired Formality Level (e.g., slider: Very Formal <-> Very Casual).
            *   Target Audience Persona (e.g., dropdown: General Public, Technical Experts, Colleagues).
            *   Primary Tone Goal (e.g., dropdown/tags: Confident, Empathetic, Neutral, Persuasive).
            *   Toggle switches for specific check types (e.g., "Check for Idiom Usage," "Flag Passive Voice").
    *   **iii. Dictionary:**
        *   Functionality to add specific words, brand names, or technical terms that the user wants the analysis engine to ignore or recognize as correct.
        *   Input field: "Add a new word".
        *   List view of added words with a "Remove" option.
    *   **iv. Security Overview:**
        *   Display signed-in devices.
        *   Recent login activity.
        *   Two-factor authentication settings.
    *   **v. Privacy:**
        *   Toggles for data usage (e.g., "Allow AuthenticText to use my content for model improvement" - clearly explained).
        *   Link to Privacy Policy.
        *   Option to request personal data report.

*   **E. Version History:**
    *   Accessible from the Document Editor view or a dedicated sidebar item.
    *   Shows a list of saved versions of a document with timestamps.
    *   Ability to view and potentially restore previous versions.

*   **F. Trash:**
    *   Lists recently deleted documents.
    *   Option to restore or permanently delete.

*   **G. (Optional) Apps/Integrations:**
    *   Similar to Grammarly's "Apps" section, show potential integrations (e.g., Chrome Extension, Word Add-in) even if they are just placeholders for future development.

**5. User Flow Considerations:**
*   Primary Flow: User Logs In -> Lands on Dashboard -> Uploads/Creates Document -> Enters Analysis View -> Reviews/Applies Suggestions -> Saves Document.
*   Settings Flow: User clicks Settings -> Navigates sub-sections -> Modifies preferences/dictionary -> Changes are saved automatically or via a Save button.

**6. Output Required:**
Generate high-fidelity mockups or interactive wireframes for the key screens detailed above (Dashboard, Document Analysis View, Settings sections, Dictionary). Ensure the design is cohesive, intuitive, and visually distinct while borrowing structural best practices. Focus on clearly presenting the unique "humanizing" suggestions in the Analysis View.

How to Use:

Provide to Lovable.dev: Copy and paste this entire prompt into Lovable.dev.

Iterate: Lovable.dev will generate an initial design. Review it against the prompt. If parts are missing or not quite right, you can provide feedback to Lovable.dev (e.g., "Make the suggestion cards more prominent," "Change the gradient on the primary button," "Add the search bar to the dashboard").

Refine: Work iteratively with Lovable.dev until the design aligns closely with the vision described in the prompt.

This prompt provides a strong foundation by outlining the purpose, structure, key features, and desired aesthetic, leveraging the Grammarly example as a structural guide while clearly defining the unique value proposition and visual direction for "AuthenticText".

## **Timelapse Experimental App Prompt**

```
**Objective:** Create a web application called "Timeforms" that visually represents the current time and weather for a specific location using dynamic graphics and gradients, closely replicating the functionality and aesthetic shown in the provided video (timeforms.app).

**Target Framework:** React (using Vite for setup is preferred)

**Core Components & Functionality:**

1.  **Layout:**
    *   Implement a two-column layout.
    *   **Left Column (Control Panel):** Width approx 30-35%. White background. Contains all user interface controls. Clean, minimalist styling for buttons, sliders, and toggles.
    *   **Right Column (Visual Display Panel):** Width approx 65-70%. Displays the generated visual. The visual itself should be contained within a subtle frame element to mimic a piece of art on a wall (light beige/off-white background for the 'wall').
    *   **Footer:** A small text line at the bottom: "Crafted with love by [Your Name/Handle] & robots. Time and weather are local to [Default Location, e.g., Cobble Hill, Brooklyn]."

2.  **Visual Display Panel:**
    *   **Text Overlay:**
        *   Position: Top-left corner within the frame.
        *   Content: Display current Temperature (in °F), Weather Condition (text, e.g., "Sunny"), and Time (HH:MM format).
        *   Data Source: Fetch real-time data (see Data Integration section). This text should update based on real-time data or simulated data.
        *   Visibility: Controlled by the "Time Display" toggle in the Control Panel.
    *   **Dynamic Visual Generator:**
        *   **Graphic Mode:** Render a series of concentric, partially transparent circles stacked vertically. The color of these circles should change based on the time of day (simulated or real-time). Dark deep purples/near black for night (0:00-5:00), transitioning to lighter purples/pinks for dawn (5:00-7:00), bright oranges/yellows/reds for daytime (7:00-18:00), fading back through purples for dusk (18:00-21:00), and returning to dark for night (21:00-23:59). Colors should transition smoothly. The number and spacing of circles should create a tunnel-like perspective.
        *   **Gradient Mode:** Render a smooth vertical gradient filling the frame. The gradient colors should follow the same time-of-day logic as the Graphic Mode (dark night -> bright day -> dark night).
        *   **Both Mode:** Overlay the Graphic mode circles onto the Gradient mode background. Implement CSS blend modes ("Overlay", "Soft Light" - assuming 'Soft' means Soft Light, "Dodge") selectable via controls.
        *   **Weather Influence:** The selected weather (real or simulated: Sunny, Mixed, Overcast) should subtly influence the color palette. "Sunny" uses the vibrant default palette. "Mixed" might introduce more blues or slightly desaturated tones. "Overcast" should significantly desaturate the colors, leaning towards greys and muted tones. Transitions between weather effects should be smooth.
        *   **Atmospheric Effects (Optional Enhancement):** If the "Atmospheric Effects" toggle is enabled (visible in Gradient/Both modes), add a subtle, configurable layer like noise, grain, or very faint moving particles over the visual.
        *   **Background Shift (Optional Enhancement):** If the "Background Shift" toggle is enabled, implement a very subtle effect on the visual's background (e.g., a slow parallax shift relative to mouse movement, or a very slow, almost imperceptible animation/oscillation of the gradient/colors).

3.  **Control Panel:**
    *   **Section: "Choose design"**
        *   Button Group: "Graphic", "Gradient", "Both". Single selection. Updates the Visual Display Panel accordingly.
        *   Conditional Button Group (Only visible if "Both" is selected): "Blend Mode" - "Overlay", "Soft", "Dodge". Single selection. Applies the chosen blend mode to the graphic overlay.
        *   Conditional Toggle (Only visible if "Gradient" or "Both" is selected): "Atmospheric Effects". Default off.
    *   **Section: "Time Simulation"**
        *   Slider: Range 0 to 23 (representing hours), potentially with finer granularity (e.g., steps of 0.5 for half hours). Label should show the selected time (e.g., "14:00"). Moving the slider updates the Visual Display Panel's colors and the Text Overlay time in real-time.
        *   Button: "Simulate a day". On click:
            *   Animate the time slider smoothly from 00:00 to 23:59 over ~15-20 seconds.
            *   Update the visual dynamically during the animation.
            *   Change button text to "Stop".
            *   If "Stop" is clicked, halt the animation at the current simulated time. Button text reverts to "Simulate a day".
        *   Button: "Return to current time". On click:
            *   Stop any running simulation.
            *   Set the slider and visual to reflect the *actual* current time.
            *   Ensure the "Simulate a day" button text is reset.
    *   **Section: "Weather Simulation"**
        *   Button Group: "Sunny", "Mixed", "Overcast". Single selection. Updates the Visual Display Panel's color palette/mood.
        *   Button: "Return to current weather". On click:
            *   Set the visual to reflect the *actual* current weather condition.
            *   Deselect the simulation buttons.
    *   **Section: "Background Shift"**
        *   Toggle Switch: Default off. Enables/disables the background shift effect.
    *   **Section: "Time Display"**
        *   Toggle Switch: Default on. Shows/hides the Text Overlay in the Visual Display Panel.

4.  **Data Integration:**
    *   Use a free Weather API (e.g., OpenWeatherMap, WeatherAPI) to fetch current local time, temperature, and weather condition (e.g., clear, clouds, rain) for a default location (Cobble Hill, Brooklyn - Lat/Lon lookup needed). Allow the location to be configurable if possible (perhaps via an environment variable).
    *   Map API weather conditions (clear, partly cloudy, cloudy, rain, etc.) to the simplified "Sunny", "Mixed", "Overcast" states for visual representation.
    *   Handle API key management securely (e.g., using environment variables).
    *   Fetch data on initial load and potentially refresh periodically (e.g., every 15-30 minutes).

5.  **Styling & Polish:**
    *   Use CSS (CSS Modules, Tailwind, or Styled Components) for styling.
    *   Ensure smooth CSS transitions for all visual changes (color shifts, gradient changes, text visibility).
    *   Maintain a clean, minimalist, modern aesthetic as seen in the video.
    *   The application should be reasonably responsive, although the primary target seems desktop. The control panel might stack above the visual display on smaller screens.

**Best Practices to Emphasize:**

*   **Component-Based Architecture:** Break down the UI into reusable React components (e.g., `ControlPanel`, `VisualDisplay`, `TimeSlider`, `WeatherButtons`, `DesignSelector`).
*   **State Management:** Use React's built-in state (useState, useContext) or a simple state management library if needed to manage time, weather, simulation states, and UI settings.
*   **Performance:** Optimize rendering, especially during animations. Use `React.memo` or equivalent where appropriate.
*   **Clean Code:** Write readable, well-commented code.
